# Private signature vision canary

This is a controlled optional mode, not a record of a production pass. The application capability is disabled until capacity, text regression and the six-document quality checks pass. Keep BF16, the existing immutable `c202236235762e1c871ad0ccb60c8ee5ba337b9a` weights, 8192 tokens, global concurrency 1 and the 0.85 memory target. No dependencies, quantization, cloud image fallback or GPU changes are introduced.

## Admission and image boundaries

`QwenClient` queues all text and vision requests in `business.private_inference_queue`, introduced by migration 035. An existing PostgreSQL session advisory lock spans the actual request; queued text is admitted before queued vision, FIFO within a kind. Waiting is bounded to 60 seconds by default. Expired queue rows cannot release an active session lock. The pipeline releases capacity after each page-discovery or crop call, so text can enter between them. API and Worker roles both require the queue's SELECT/INSERT/DELETE grants. Unknown transport outcomes remain ledger-unknown and are never automatically resent.

The new private transport accepts one PNG byte buffer with its exact SHA256/dimensions, maximum 10 MiB and 16 MP. It accepts no image URL, file path, multimodal embeddings or arbitrary message parts. The inference server only allows the reserved `image-download-disabled.invalid` media domain, has no permitted local media directory, and disables media disk/processor caches. The application emits only inline data URLs to its private Qwen service. Existing cloud transports remain text-only. The proxy body limit is 15 MiB to accommodate base64 overhead; the bounded application byte limit remains authoritative.

Whole-page discovery produces at most 12 regions; candidate regions receive surrounding original pixels and, when the same crop pixel budget permits, the full horizontal signing row for local verification, with a translation back to the page. Substantially identical input contexts may share a crop; this never merges independent observations or counts people. The verifier emits a single visual label, and the program derives the public kind/reason pair. Historical responses with contradictory separate kind/reason values are not retrospectively reinterpreted. Crops larger than 1,048,576 pixels are reported as incomplete rather than silently shrunk. The vision processor may reduce whole-page input to its independent 1,048,576-pixel budget. An image that is unreadable, a truncated region or local-observation list, malformed geometry, a mark clipped at an artificial crop edge, an oversized crop or confidence below 0.8 is not a negative finding. Neither model observations nor printed names establish the signer's identity.

## Deployment and capacity procedure

1. Use the application release lock, drain document/intake work, verify no active model calls, and back up the current GPU launcher, Nginx config, mode file (including absence), dependency/model locks and status. Do not run direct canaries concurrently with application work because a loopback probe intentionally has no application database session.
2. Before changing mode, run `/data/hsbc/envs/vllm/bin/python /data/hsbc/scripts/verify-vision.py --text-only --report-dir /data/hsbc/run/vision-TIMESTAMP-text`. The script creates a fresh private report directory and records sanitized timing, token and GPU metrics only.
3. Copy the reviewed launcher, Nginx config and canary script. Run `vllm serve --help` under the existing environment and verify the exact flags in the launcher; inspect the pinned processor's supported `max_pixels`/`min_pixels` options. Run `nginx -t -c /data/hsbc/config/nginx/nginx.conf`. Keep application vision disabled.
4. Write exactly `vision` to `/data/hsbc/deploy/qwen-mode`, restart only the dedicated `hsbc-qwen` process and reload its Nginx. Wait for authenticated readiness. Do not add `--skip-mm-profiling`, raise the memory target, shrink text context or silently switch models to make startup pass.
5. Run the existing `verify.py --inference`, then `/data/hsbc/envs/vllm/bin/python /data/hsbc/scripts/verify-vision.py --report-dir /data/hsbc/run/vision-TIMESTAMP-mm --baseline /data/hsbc/run/vision-TIMESTAMP-text/capacity.json`. The canary checks text before/after, blank signing lines, printed names, a synthetic stamp and a 16 MP input. Every request must finish normally on the pinned model, GPU headroom must remain at least 1024 MiB, and median text latency must not exceed 2.5 times the recorded baseline. This proves bounded runtime feasibility, not document recognition accuracy.
6. Run the application-level private client/text regression and shared PostgreSQL admission test. First evaluate the actual `reviewPage` pipeline on frozen synthetic positive/negative controls, then an independently annotated blind holdout. Runtime canary success is not this quality gate. Only after these pass, evaluate the original six-document allowlist against its independently annotated 69 pages. The original pages contain no clear handwriting/full-stamp positives, so their positive recall is not measurable; the separate controls cover visible mark positives, black/red seals, rotation, overlap and negative controls. Record false positives, misses and unknowns separately. Keep the capability disabled until the independent configuration approval and acceptance gates have passed.
7. Resume application work only after the selected mode is ready and API/Worker/Web carry the matching release. Retain sanitized reports and exact script/config hashes in the release receipt.

On any startup, memory, latency, text regression or visual-quality failure, keep application vision disabled, write `text` to the mode file (or restore its original absence), restore the previous launcher/proxy configuration if necessary, restart the dedicated Qwen service and rerun `verify.py --inference`. Preserve the failed canary receipt. Do not automatically send images elsewhere. Existing text service has priority over enabling this feature.

The current flag choices follow the pinned [vLLM 0.31.0 serving interface](https://docs.vllm.ai/en/v0.31.0/cli/serve/) and [media connector](https://github.com/vllm-project/vllm/blob/v0.31.0/vllm/multimodal/media/connector.py); the Qwen model's vision capability is described by its [publisher](https://huggingface.co/Qwen/Qwen3.5-9B). The installed, pinned code and measured canary remain the deployment authority.


## Recorded quality boundary (2026-10-19)

The private runtime passed capacity and text regression checks, but the actual `reviewPage` candidate `private-signature-vision-v5` did **not** pass the frozen nine-control quality gate: 5/9 controls, 5/6 independently marked positive regions, no extra/duplicate positive marks, and failures in overlapping handwriting, blank-field localization, printed-name localization and table-line exclusion. The one-to-one evaluator (`signature-controls-one-to-one.v2`, IoU 0.30) records missing regions, unrelated extra detections and duplicates separately. Earlier evaluation receipts remain unchanged; the former any-match scores are not equivalent to the stricter one-to-one accounting.

The final round made 28 completed private calls and retained zero unknown calls. No blind holdout or original 69-page recognition run was started. The fixed 9B model and current pipeline remain insufficiently reliable for enabling signature checks. The application capability stays disabled, and the GPU service is restored to the original verified text configuration after each failed quality window. Passing unit tests or the runtime canary must not be presented as recognition acceptance.
